# Directory import

Builds unclaimed listings from public business data at low cost. Records are staged, checked and reviewed; nothing reaches the public site until someone on the ops team approves it at `/ops/import/review`. Owner-confirmed data and staff edits always win over imported data.

## One run does everything

An import run is one pipeline; nothing has to be started separately afterwards. In order: discover the businesses (DataForSEO), read each business's own website, use the extra sources for whatever is still missing (Google Maps, the business's Facebook page and Instagram profile through Apify; sites our crawler could not load are read again in the worker's own browser; each only where a record still lacks a template section), then ChatGPT web research for what is still open (facts only with the page they were read on), photos from Google posts, the writer (ChatGPT by default) on the full evidence, then the checks. Every record then carries its readiness against the profile template (`profileStatus`, `coverage`) and waits in the review queue; approval copies the images. The run card shows the stage the run is in (`stats.stage`), the counts in plain words and the average readiness. With `autoPublish` in the scope (an option on the new-run card, off by default) records that pass every check are published by the worker without a person looking; anything that needs a look stays in the queue.

## Stages

**Stage 1: discovery with DataForSEO** (`scripts/import/stages/dfsDiscover.ts`, provider client `scripts/import/providers/dataforseo.ts`, mapping `src/lib/import/dataforseo.ts`).

- Business Listings Search (live), one request per page of up to 1,000 records. Tasks are *area x category chunk* (at most 10 category ids per request, results filtered to country code IL). A city uses its centre and radius from the catalogue; "all Israel" uses one circle over the country.
- Every page is a unit of work with a stable request key (`dfs:<task>:<page>:<staff resend>:<retry>`):
  1. check the kill switch, the run's record limit and its budget;
  2. reserve the page's gross maximum cost (atomic, see Costs);
  3. checkpoint the task as `dispatched`;
  4. send, then commit the cost DataForSEO reports;
  5. store items and checkpoint `offset` / `offset_token`.
- A request that was sent but got no answer (timeout, reset) counts as spent and the page becomes **needs_reconciliation**. It is never resent automatically. On the run card staff either keep it as billed or mark it not billed, optionally sending it again under a new key.
- A fatal provider error (authorization, payment, balance) stops the run with the provider's message. Rate limits and 5xx get at most three retries with backoff.
- Each place is stored once: the key is the Google place id when DataForSEO returns one, otherwise `dfs:cid:<cid>`. Items without coordinates are skipped. The number shown is "matching records in the provider's database", not the number of businesses in Israel.
- What the provider said is kept as **field observations** (value, source URL, retrieval and source-update times, confidence, publishable flag). Ratings and photos are stored as observations but are not publishable until the provider's terms are confirmed (setting `publishProviderRatings`).

**Stage 2A: the business's own website** (`scripts/import/crawl.ts`, `stages/enrich.ts`, extraction `src/lib/import/siteExtract.ts`, classification `src/lib/import/websiteKind.ts`, service vocabulary `src/lib/import/services.ts`).

- **Self-hosted crawler.** The site crawler is our own code on [Crawlee](https://crawlee.dev) (`BasicCrawler`, one in-memory request queue per site, nothing written under `./storage`), with the transport still `safeFetch` (SSRF checks, size and time caps, conditional requests). Links are ranked on the queue: contact and branches pages first, then prices, then the other relevant pages, with the site menu read from the homepage. When a page comes back as a JavaScript shell (almost no text, scripts present) it is rendered at once in the worker's own headless Chromium through Crawlee's `PlaywrightCrawler` (`scripts/import/crawlee/browser.ts`), capped per run (`browserFallback`, on by default, `browserMaxPerRun`). No provider is involved and nothing is billed. The browser loads no images, media or fonts, connects directly (no ambient proxy), and every navigation and sub-request goes through the same URL and resolved-address checks as the HTTP crawler.

- **What counts as the website.** Every website value (from the provider or typed by staff) is classified first:
  - *own site* or *social profile* (Facebook, Instagram, TikTok, YouTube page): kept as the website;
  - *link-in-bio page* (Linktree and similar): read once to find the real site, socials and booking link;
  - *booking page* (Tor4You, Fresha, Calendly…) and *WhatsApp link*: moved to the booking and WhatsApp fields;
  - *directory or third party* (easy, b144, Dapei Zahav, Google Maps, Waze, health funds, gov.il, review and delivery sites, shorteners): never kept. The link is recorded as a rejected observation and shown on the record.
  Staff edits are validated the same way.
- **The site must belong to the business.** After reading it, its phones, site name and domain are compared with the listing. A site that shows its own phones and another name is dropped as *unrelated* (its emails and phones are not used). A site with nothing to compare is kept and flagged "website unverified" for review.
- Social profiles are kept as links but not read (login walls and platform terms). An account is **verified** (and published) only when the business's own site links to it, when its handle equals the site's domain label, when the provider and a link-in-bio page both name it, or when the owner entered it. A same-name account from the provider alone stays in `socials` for review and is not shown (`src/lib/import/socials.ts`).
- **Progressive page budget.** The first `crawlMaxPages` (default 5) relevant pages are read: contact, prices, services, gallery, team, about, branches, videos, found through same-site links and one bounded read of `/sitemap.xml`. The budget extends once to `crawlMaxPagesExtended` (default 12) only while template fields are still missing (phone, email, hours, three services, a price, five photos, a team member, a description) and stops as soon as they are covered.
- **Profile facts** (`src/lib/import/profileExtract.ts`): people named with a role on the site (name + role cards in either order, a name and role on one line such as "ד"ר יוסי גוברין - מנתח פלסטי", or a name followed by a biography that opens with the role; the paragraph under the card is the biography; roles are matched as whole words and include surgeons, medical and paramedical titles; testimonial signatures, menu labels, form labels, skip links, treatment names and the business's own name never become people; a line that names its own person is its own card and never the role of a neighbouring line; a single card on a non-team page does not count). The same check (`cleanTeam`) is a quality gate wherever team data enters a listing or a page: at approval and completion, on facts from ChatGPT research, and when the public profile renders, so entries an older reader stored wrongly are never shown, YouTube ids and channel links, languages only from an explicit "we speak" statement (never the site's own language), the founding year from "since" wording (never years of experience or post dates). Images on a before/after page or with a before/after caption are kept as candidates that wait for the owner's confirmation and are never published by the import.
- **Prices** keep their published form: fixed, from, range (with the upper bound), per unit / ml / area, package (with the session wording), published free, and **on_request** when the site lists the service without a price. An unknown price is stored as null, never 0, and the profile shows "המחיר לא פורסם" with a "לקבלת מחיר ופרטים" action that carries the business, branch and service ids. Imported prices are stored as published (tax status unknown); nothing is converted or assumed.

**Stage 2C: editorial writing** (`src/lib/import/editorial.ts`, `scripts/import/editorialCall.ts`, `stages/editorial.ts`). The writer is ChatGPT by default (setting `llmProvider: openai`, model `IMPORT_OPENAI_MODEL`, default `gpt-5-mini`, through the Responses API with a strict JSON schema); Claude stays available as the alternative (`llmProvider: anthropic`, `ANTHROPIC_API_KEY`). The prompt, the checks, the repair call and the cache are the same for both.

- One structured call per profile on a compact **evidence packet** (name, city, address, categories, services with prices, hours, which contact channels exist, verified socials, team, languages, founding year, accessibility, parking, the business's own description and FAQs, rating, media counts). Never the raw pages, never raw phone numbers or emails.
- Output: the Hebrew description (450 to 550 words, short paragraphs, third person), five to eight FAQs each with the packet fields it rests on, meta title and description, one-line service summaries, the section heading (על הקליניקה / על המספרה / על הספא / על הסטודיו / על העסק), and `insufficientEvidence` with the missing items.
- Deterministic checks after the call: every number, price, year and named person must exist in the packet; no em or en dashes; no generic praise, no first person as the owner, no exclamation marks, no Markdown, no booking-through-BeautyFind claims when native booking is off; FAQ count and lengths; meta lengths. At most **one repair call** with the exact problems; the draft with fewer problems is kept and the rest are shown in admin.
- Runs `llmConcurrency` calls in parallel (default 6, up to 12; the same setting paces the research and extraction stages), so a run of 300 descriptions takes about an hour instead of three; the cost per business does not change. Cached by `sha256(packet) + PROMPT_VERSION`; the same evidence is never paid for twice. A reservation left behind by a worker that was stopped mid-call (the job's time limit, a crash) is released and taken again on the next pass; a settled entry whose draft never reached the record gets a fresh key. Every pass must move the queue: ten passes in a row of rate limits or outages stop the run with the reason (continue it later), and rows that make no progress at all are marked skipped with the reason instead of being selected forever. Reserved against the run budget and the per-run editorial cap (`editorialBudgetUsd`, `editorialMaxPerRun`) before dispatch, settled at the token cost the API reports (`editorialCostUsd`, by provider). Models: `IMPORT_OPENAI_MODEL` (default `gpt-5-mini`) for ChatGPT, `IMPORT_EDITORIAL_MODEL` (default `claude-sonnet-5`) for Claude. The packet also carries the cited notes from the research step (`researchNotes`), which the writer may use like the site's own text.
- A draft under 450 words is stored as it is with `needsMoreInfo` and the missing evidence; it fills an empty description but never replaces existing text. A complete draft replaces our earlier imported text on unclaimed listings; owner text (claimed, or `ownerApproved`) is never touched. `IMPORT_EDITORIAL_MOCK=1` (tests, simulation) uses the deterministic template draft instead of the API.

**Stage 2D: media and videos** (`src/lib/server/importMedia.ts`, `src/lib/import/youtube.ts`).

- **Which images.** Size variants of one file (WordPress `-300x200`, `-scaled`, Wix and Google sizing) count once and the plain file is fetched first. Every photo is scored (`src/lib/import/imageQuality.ts`) from its pixel size, bytes per pixel, shape, and sharp's statistics: entropy tells a photograph (6 to 8 bits) from a flat graphic (0 to 4), an alpha channel marks a cut-out or logo, and a perceptual difference hash finds the same picture resized or re-encoded. Decoration is rejected by filename and alt (backgrounds, patterns, badges, certificates, maps, icons, stars). A few more candidates than needed are read so the ranking has a choice: the cover is the best landscape photograph, the gallery follows by score, and the copies that did not make the cut are removed from storage again. `IMPORT_IMAGE_QUALITY=0` (tests and the simulated pilot, whose fixture images are flat colours) keeps only the size rules. Logo candidates come from the site (JSON-LD logo, the image inside a header block marked logo or brand, an image with a logo hint, a large touch icon or PNG site icon), from the Google profile (DataForSEO) and from the business's confirmed Facebook and Instagram profile pictures (Apify). Every candidate is read and the best mark wins (`logoScore`: transparency and a compact shape count for; photographic entropy, a wide strip and partner, payment or award badges count against); the others are removed again. Video posters: the YouTube thumbnail of each playable video is copied into our storage (`copyVideoPosters`, 640px WebP) when images are copied, so the card shows the real cover without a request to YouTube before the visitor presses play.
- Each copied image keeps a provenance record on the listing (`mediaProvenance`): source asset URL, page or profile, provider, retrieval time, dimensions, bytes, sha256 (duplicates dropped), alt text, reuse basis (`business_published`: the business's own published material about itself), status and derivative type. The served file is a WebP (orientation corrected, metadata stripped, banner up to 1600px, gallery 1200px, logo 512px; quality lowered until the banner is about 350KB and gallery images about 160KB); the safe original is stored privately next to it. The first landscape photo becomes the banner. A listing with no approved photo shows a neutral branded monogram and `hero_media_missing` in admin; nothing is generated or borrowed.
- YouTube: ids found on the official site are validated (Data API `videos.list` in batches of 50 when `YOUTUBE_API_KEY` is set, 1 quota unit per call; otherwise the public oEmbed endpoint, no key, no quota). With the key, the verified channel's uploads are read (2 units) when fewer than `youtubeMaxVideos` playable videos were found. Quota is counted per run (`youtubeQuotaPerRun`). Only public, embeddable videos reach the profile, as click-to-load `youtube-nocookie` players behind the embed consent. Nothing is downloaded or rehosted.

**Stage 2E: Apify actors for the remaining gaps** (`src/lib/import/apify.ts`, `scripts/import/providers/apify.ts`, `scripts/import/stages/apify.ts`). Three actors, inside import runs (after the website stage) and enhance runs, for the records whose plan names the step. Google Maps, Facebook and Instagram stay on Apify on purpose: reading them with our own code would mean login walls, blocks and the platforms' terms, and the rules below say stop on a block rather than work around it.

- **Google Maps** (`compass~crawler-google-places`, by place id or cid): opening hours, phone, website link, wheelchair access and parking as tri-state facts, the owner's own profile description (used like the DataForSEO description: evidence, and a fallback text only where the record has none), profile photos as image candidates (`useProviderImages`), rating and review count (`publishProviderRatings`), closure state (a permanently closed place gets the `closed_on_google` review reason). Review texts are never requested (`maxReviews: 0`).
- **Facebook page** and **Instagram profile** (`apify~facebook-pages-scraper`, `apify~instagram-profile-scraper`): the profile is read only when the record names an account, and its facts are taken only when **the profile itself confirms the business**: it links to the business's website (`profile_links_site`) or shows the business's phone (`profile_shows_phone`). A same-name account that does neither is marked `no_match` and nothing is taken from it. A confirmed account is verified and published; its about or bio text becomes evidence for the editorial packet (`profileTexts`), its email and phone fill empty fields, its website link fills a missing website, the Facebook hours fill missing hours, and the profile picture, cover photo and recent image posts (`apifyMaxPosts`) become image candidates with `instagram` / `facebook` provenance.
- **Rendered website, self-hosted** (`scripts/import/stages/render.ts`, step `render`, switch `apifyRender`, pages per site `apifyRenderPages`; the setting keys keep their old names). Only for sites our own crawler could not read (status `failed`, or a JavaScript shell that returned no services, description or photos). The worker's own Chromium opens the homepage, follows the site's contact, branches, prices and other relevant links, and the rendered pages go through the same `extractPage` and become the domain's cached site summary (`via: browser`), which the website stage then reads like any crawl (`requeueAfterSources`). Sites that blocked us or forbid crawling in robots.txt are never rendered: the planner leaves them out and robots.txt is checked again before the browser opens. No Apify token, no charge; a worker without Chromium marks the tasks failed with the install hint (`renderNoBrowser` on the run).
- **Money.** Each actor task (a batch of up to 50 places, 50 profiles or 20 pages) reserves its gross maximum at `pricing.apify.reserveFactor` (2) times the per-item rate against the run budget, the per-run Apify cap (`apifyBudgetUsd`) and the monthly cap (`apifyMonthlyUsd`), then starts the actor. The actor run id is written on the task at once, so a worker that stops mid-way resumes the same run instead of paying for a second one. The recorded cost is the run's `usageTotalUsd`. A start that fails for credit or token reasons stops the run with the message (the recover buttons apply); other failures skip the batch. A start without an answer is `needs_reconciliation`. Per-record cost shares land in `costs.apifyUsd`.
- Prices in `pricing.ts` are recalled reference rates, marked unverified: confirm them on the actor pages before a live run and override with `IMPORT_PRICING_JSON`.

**Stage 2F: ChatGPT web research for the remaining gaps** (`src/lib/import/openai.ts`, `scripts/import/providers/openai.ts`, `scripts/import/stages/research.ts`). Runs after the Apify sources, inside import runs and completion batches, for records whose plan names the `research` step (a key is set, `openaiEnabled` and `researchEnabled` are on, and the record was not researched in the last 30 days).

- One Responses API call per record with the `web_search` tool (`user_location` Israel, at most `pricing.openai.research.maxSearchCalls` searches) and a JSON schema answer. The model is told what the record already has and what to look for, derived from its missing template sections (`researchTargets`): website, phone, email, WhatsApp, social accounts, booking page, opening hours, services with prices, team, languages, founding year, accessibility, parking, and short factual notes.
- **Every fact needs the URL of the page it was read on.** A fact without a usable URL is dropped before it reaches the record (`researchFacts`, counted in `crawl.research.dropped`). What survives is stored as field observations with provider `openai_research` and that URL, and only **empty** fields are filled (staff edits are never touched). A website the model names goes through the website stage afterwards, which decides whether it belongs to the business. An email found by search is filled only when its domain has mail records and is marked `emailSource: search` for a person to confirm; it is never published from this source alone. Social accounts found by search stay unverified until a profile or the site confirms them. Services arrive with the quoted line and become imported services with their published price form.
- The outcome is written on the record (`crawl.research`: targets, filled fields, sources, notes, notFound, cost, search calls, model, version, attempts) and shown in the report and the review checklist.
- **Money.** Each record reserves `pricing.openai.research.perRecordUsd` against the run budget, the per-run research cap (`researchBudgetUsd`) and the monthly cap (`researchMonthlyUsd`), then settles at the token and search usage the API reports (`openaiCostUsd`). A record over a cap is skipped and the run says which cap. A quota or key error stops the run with the message (recover buttons apply); other errors skip the record. A request key per record and attempt means a stopped worker does not pay twice for the same attempt. OpenAI rates in `pricing.ts` are unverified reference values: confirm them on the pricing page and override with `IMPORT_PRICING_JSON`.

**Enrichment plans** (`src/lib/import/enrichPlan.ts`). Every step (DataForSEO refresh, the four actors, re-reading the site, ChatGPT research, editorial writing, rewriting, copying images) declares which template sections it can fill and when it applies (a source exists, the provider is on, the token is set, the kill switch is off). "All enrichments needed" runs each step only for the listings whose missing sections it can fill; manual mode runs the chosen steps for every chosen listing. The same rules and the same per-step estimate are used by the tab and by the worker when it seeds the run, so a batch never spends more than the tab showed.

**Coverage and readiness** (`src/lib/import/coverage.ts`, `docs/coverage-manifest.md`). Every visible template element has a manifest entry (implementation, data, source rule, honest fallback, action, test). `coverageOf()` scores a listing into two separate numbers, template coverage (every section renders content or a truthful state) and evidence readiness (weighted sections filled with sourced content), and classifies it as `ready`, `ready_with_disclosed_gaps`, `needs_owner_information` or `needs_review`. The result is stored on the listing and the record (`profileStatus`, `profileChecklist`) and shown in the admin checklist.
- Plain HTTP only, as `BeautyFindBot/1.0`, respecting robots.txt, with a pause between pages. Home page plus up to 5 relevant pages (contact, prices, services, gallery, about), depth 2 or less; it stops early once it has an email, a phone and at least three priced services.
- **Services.** Read from JSON-LD offers, price lines with the name before or after the price, card layouts (name, then price on the next line), ranges and "from" prices, and short menu items that name a known treatment (listed without a price). Each service gets one of our categories, a medical flag, a duration when written, and the line it came from. Services are merged with what the record already has (a price fills a missing one; nothing is dropped). A category is added when the site has one priced or two listed services in it (unless staff edited the categories). On approval, unpriced services are saved but hidden until the owner prices them.
- **No website of its own.** When a business has no own site or social profile (or its link was a directory or another business's site), its Google profile link (Maps, by cid) becomes the website.
- **Google rating.** The Google rating and review count from DataForSEO are kept for every business that has reviews and published with a link to its Google profile (`publishProviderRatings`, on). Review texts are not collected.
- **Logo and photos.** The Google profile logo and main photo (DataForSEO, larger rendition) are candidates for every business (`useProviderImages`, on) and are used when the site has none. Logo candidates (JSON-LD logo, header logo images, touch icon) and photos (large content images, lazy-loaded and srcset images at their largest size, og:image, JSON-LD images) are collected; icons, SVG, GIF, tracking pixels and social or payment badges are skipped. The best logo and up to `maxListingPhotos` photos are pre-selected; staff can change the choice in review. On approval the chosen files are downloaded through the same SSRF-safe fetch, checked to be real JPEG/PNG/WebP files of a usable size, stored in our own storage and set as the listing's logo, cover and gallery. Nothing is hotlinked. Controlled by `useWebsiteImages` (on by default).
- Reads mailto/tel links, JSON-LD (`telephone`, `email`, `address`, `openingHoursSpecification`, `sameAs`), explicit WhatsApp links, social profile links and known booking hosts. Every fact keeps its page URL and a short evidence snippet.
- The site builder's footer email ("נבנה ע"י…", "powered by…") is set aside, never used.
- Emails get a status: `dns_valid` (the domain accepts mail) or `syntax_valid`. Mailboxes are never probed over SMTP.
- Phone and opening hours come from the Google Business Profile (DataForSEO, Maps) or the business website only. The provider's phone stays; the site's number fills it only when the site shows exactly one number. A different number, or hours that disagree, is a **notice** on the record (the Google value stays, the site's value is in the evidence table); it never holds the record. Facebook, Instagram and ChatGPT research keep their phone and hours as evidence only and never write them.
- An explicit block (401, 403, 429, 451, a challenge page) stops that site. No proxies, no challenge bypassing.
- Results are cached per domain (`site_fetches`): one crawl serves every branch on the same domain; conditional requests (ETag, Last-Modified) and content hashes avoid re-reading unchanged pages; rechecks after 30 days, or 7 after a failure (negative cache).
- SSRF protection (`src/lib/import/safeFetch.ts`): only http/https on ports 80/443, no credentials in URLs, DNS checked at connect time so the address connected is the address checked, every redirect (at most 5) checked again, private/loopback/link-local/metadata ranges refused, size and time caps.
- Optional and off by default: an LLM step (`llmEnabled`, `llmBudgetUsd`) that returns categories and treatments only with a quote from the page; it adds services and fills missing prices but never replaces what the site stage found.

**Stage 2B: Google Places (New), selective** (`src/lib/server/googleDisplay.ts`, `src/lib/import/googleFields.ts`).

- Off unless `GOOGLE_ENRICHMENT_ENABLED=true` in Vercel **and** the admin switch is on. The kill switch wins.
- Used only when a staff member presses "אימות מול Google" or "דירוג ב־Google" on a record. Never on page views, cards, crawlers or at import time.
- Explicit allowlisted field masks, never `*`. The SKU is taken from the highest-tier field in the mask. Each call is reserved against the daily and monthly caps first.
- Google content is shown in a separate, attributed panel and never copied into listing fields, exports, logs or analytics. Only the place id is kept permanently and the location for 30 days (`google_display`, deleted on expiry by the sweep that runs before each lookup and at the start of each worker).
- Photos: off (`googlePhotoCap` 0). When enabled, one photo URI per lookup, capped per day, never stored.

**Listing template.** Every field the listing page shows has a source, in this order:

| Field | Sources |
|---|---|
| Phone, address, map pin | DataForSEO, then the site |
| Email | The site (contact page first), then DataForSEO contact info |
| Website | Own site, else social profile, else the Google profile link |
| WhatsApp, Instagram, Facebook, booking link | The site, the Google profile's reservation link |
| Opening hours | DataForSEO, then the site (JSON-LD, then hours written as text: "א'-ה' 09:00-19:00", "Sun-Thu…") |
| Logo, cover, gallery | The site's images (gallery pages read early), then the Google profile logo and main photo, then photos from the business's own Google posts when it still has fewer than five; picked in review, copied on approval (up to 8; the gallery shows 5). A photo that fails the size check is replaced by the next candidate. |
| Description | The Google profile description, then the site's own (JSON-LD, meta description), else a factual summary built from the record (categories, city, services, rating) |
| Services and prices | The Google profile's services, the site's price lists and menus |
| Categories | Provider categories, plus categories the site clearly offers |
| Google rating and review count, Google profile link | DataForSEO |
| Wheelchair access, free parking | Google attributes, then explicit statements on the site |
| FAQs | The site's FAQ (JSON-LD FAQPage or question/answer blocks) |
| Waze link | Built from the map pin |

The review screen shows each record's completeness and what is still missing.

**Google post photos** (`stages/googlePosts.ts`, setting `googlePostPhotos`, on). For records with fewer than five photos after the website stage: DataForSEO Google business updates (the business's own posts), up to 100 tasks per request, reserved against the run budget at an unverified $0.004 per task (the reported cost is recorded), collected for up to 20 minutes.

**Page title.** Every imported listing gets one title shape, built by `src/lib/seo/listingTitle.ts` to win searches for the business itself: the exact business name, then the city, then the main category, then "מחירים, ביקורות ושעות פתיחה", trimmed tier by tier to 60 characters (the layout appends " | BeautyFind"). A city or category the name already contains is not repeated. The writer's `metaTitle` stays in the draft; the profile page uses the built title for every unclaimed listing, and an owner's own title once the listing is claimed.

**Text safety.** Provider and website text is cleaned before it is stored (`src/lib/import/text.ts`): lone UTF-16 surrogates (an emoji cut in half by a character-count truncation) and control characters are dropped, truncations count code points, and the worker's database client cleans every write, so a Facebook or Maps description with emoji can no longer fail a stage with "unexpected end of hex escape".

**City.** A record whose locality never matched a catalog city (an English spelling such as "Tel Aviv-Yafo", or an older run) is resolved again by the checks stage and by the single-record recheck: English spellings of every catalog city are aliases, and coordinates inside a city's area decide otherwise.

**Branches pages and the site menu.** The crawler follows the site's own menu (links inside nav, header and menu elements) one level down from the homepage, so a section the menu names is read whatever its path looks like, and it puts a branches page ("סניפים", locations, clinics) right after the contact page. While the site links to a branches page and none was read, the page budget stays open for it. On such a page every location block (heading, address, phone, email, hours) is extracted (`src/lib/import/locations.ts`); the website stage then picks the block that names the record's city (or its name suffix, or its street) and takes that block's phone, email, hours and address for the record, with the site's central number only as a fallback. The enhancement "site" step runs the same code, so an existing listing gets its branch's details on the next completion batch.

**Chains and franchises.** Import records that share one business website (proportsia.co.il with branches in several cities) are one business with several branches. The website domain is the chain key (`src/lib/import/chain.ts`, `businesses.chain_key`): when a record is published, a business already holding that key whose branch names match (same first distinctive word, or names mostly alike) receives the new branch instead of a new business being created; an unrelated name on the same hosting domain stays separate. The review screen shows "רשת: N סניפים" on such records. On the claim flow the owner sees the other live, unclaimed branches of the business under "סניפים נוספים של העסק" (all selected by default) and claims them in the same request; on approval the selected branches join the account, and any branch left out moves to a business of its own so it stays public and claimable. Billing stays per branch: every live branch is charged the plan price, and from the fourth branch on each extra branch gets 25% off (`chainTotal` in `src/lib/pricing.ts`).

**Emails on the website.** Every address on a read page counts: mailto links, Cloudflare-protected ones, plain text, addresses split across inline tags or written with spaces around the @ or with "at" and "dot". A mailbox on a domain that is the site's name spelled slightly differently (proportsia.co.il and info@proportzia.co.il) counts as the business's own domain, for ranking and for the domain-mismatch note. A builder credit next to an address on another domain marks it as the agency's mailbox only when nothing around it says it is the business's contact block (phone, email, hours labels).

**Duplicate control.** Three layers: the provider's place id is the record key (`import_places.place_id`), so a business found again by any run or provider updates the same record instead of creating a second one; the checks stage scores every open record against every other import record and against every live listing (`src/lib/import/match.ts`: name similarity, distance, phone, email, website, place id) and marks strong matches `duplicate` or `merged` automatically, weaker ones "needs review" with the reasons shown; and the coverage counts above keep a city and category from being crawled twice by mistake.

**Claim line.** An unclaimed listing carries one short call to action under the business name ("העסק שלכם? לאימות בעלות") that opens the claim flow on that listing (`/for-business/claim?branch=<id>`, kept through the business login), so the owner verifies the listing they came from rather than searching for it; the contact card repeats the invitation where the enquiry form would be.

**Team section.** Only verified staff members (added by the owner after claiming) appear in הצוות שלנו. Names the crawler finds on a website are kept on the import record for the review screen but are never published, never counted as a gap, and never sent to any enrichment step.

**Rewriting after publication.** The profiles report has "כתיבה מחדש" on every group row (all published, unclaimed listings in that city and category) and "כתיבה מחדש של התיאור" on every published listing card. Both start an enhancement batch with the `editorial` and `regenerate` steps, one writer call per listing, and the new description and FAQs replace the old ones (an owner-approved text is never replaced). The same steps are available under "customise" on the enrichment tab and on the review record.

**About text.** The description shows its first 250 words; "קראו עוד" reveals the rest in place. The full text is always in the HTML.

**Fact cards.** Only sourced facts get a card (founding year, team, languages, then responsibility, today's hours and the Google rating as alternates). Fewer facts mean fewer cards; no placeholder card is shown. Service groups start closed.

**Empty sections stay off the page.** The public profile shows a section only when it has content: description, services, reviews (a Google rating or a verified review), before and after, team, videos, hours and FAQs are left out when nothing is known, and the phone chips list only the sections present. Identity, location and contact always render. The readiness score still counts the missing sections, so the admin sees what to fill.

**Listing addresses.** Listings live at `/:region/:category/:slug`. The category is the listing's **primary** category (`branch_categories.is_primary`, set at approval from the record's first category; older rows without the flag fall back to catalog order). The slug is the business name, readable and without a random tail (`src/lib/import/slug.ts`): a Latin name becomes `ehud-elbaz-beauty-salon`, a Hebrew name keeps its Hebrew letters; when the slug is taken the city is appended, then a counter. `/:region/biz/:slug` and any other category redirect to the canonical address permanently (308), so old links keep working. The rewrite in `next.config.ts` only matches category slugs, which never overlap with city slugs.

**Primary category** (`src/lib/import/categoryRank.ts`). A record's categories are ordered by evidence, and the first decides the address and the card: the business name (מספרה, ציפורניים, ספא, hair, nails...), Google's primary type (strong, except generic types such as "beauty salon"), Google's additional types, and the site's price list (services matched per category). A category the name or three services support joins even when Google did not list it. Ranked when the provider item is mapped and again after the website is read; a staff edit of the categories is final.

**Region-named cities.** חיפה and ירושלים carry their region's name, so `/haifa/haifa` redirects to `/haifa` and links point there; their city and category pages (`/haifa/haifa/facials`) keep their own address.

**Enhancing published listings** (`stages/enhance.ts`, `src/lib/server/importEnhance.ts`). A separate run type, started from `/ops/import` ("העשרת עסקים שפורסמו") or for chosen records on the review screen's approved tab. For live listings that came from the import and that no owner has claimed:
1. optionally refreshes the DataForSEO data (one request per up to 500 listings, filtered by cid, reserved against the run budget);
2. reads each business's website again;
3. fills only what the listing is missing: contact details, hours, description, FAQs, accessibility, parking, Waze and Google profile links, logo, cover and gallery (copied to storage), categories, services and missing prices. The Google rating is refreshed. Nothing that is already on a listing is overwritten, and claimed listings are never touched.
The worker needs `BLOB_READ_WRITE_TOKEN` as a GitHub secret to copy images; without it the run fills everything else and reports how many listings are waiting for images.

**Checks** (`stages/check.ts`). Over every open record, not only this run's:

- Duplicates: automatic only for the same place id, or a shared phone/email plus a matching name. A shared domain or a chain's central phone never merges two branches. Weaker matches go to review.
- Existing listings: compared with every live branch. A possible match goes to review with a merge button.
- Publication minimum (settings): name, category, a location, and a phone or an email (`requirePhoneOrEmail`, default). Email alone can be made mandatory (`requireEmail`, off). Possible duplicates, an unverified website, an unknown city and similar go to review. Notices (`NOTICE` in `rules.ts`: a medical category, a phone or hours that differ on the website) are shown on the record and never hold it. Staff-edited fields are never overwritten by a rerun.

## Admin (`/ops/import`)

Only the `ops` staff role. Every action is written to `audit_logs`. Four screens, shown as tabs on every page:

- **ייבוא וריצות** (`/ops/import`). *New import*: name, categories, cities or all Israel, how many businesses. Next to every category and city the form shows **found / total**: the provider's count of businesses there (a paid count run, one request of one record per city and category, `scripts/import/stages/count.ts`, stored in `import_coverage`) against what the import already found for the selected categories, with a check mark once the pair is covered (90% or more), so the same city and service is not crawled twice. The panel under the scope sums the selection (total, found, published, what is left) and offers "count businesses" for the pairs never counted or counted more than 30 days ago (with the request count and the price), a recount, and a button that sets the record limit to what is left; the card lists what the run will do step by step with the connection state of each source, shows the gross estimate per source (DataForSEO, Apify, writing) and sets the run ceiling from it (a manual ceiling, automatic publication and the legacy Google provider are under "more options"). "Try on 10 businesses" runs the same pipeline on ten records. *Published businesses*: how many listings the enrichment tab can complete, with the copy-pending-images button. *Sources and connections*: every source in one place with its status (from `settings.workerStatus`, which the worker writes at every start; Vercel keys are read directly), its on/off switch, what it does and where its key lives; the ChatGPT row has the research switch, the writer switch and the writer choice (ChatGPT or Claude); caps and publication rules, then advanced settings, are folded away. The kill switch stays at the top. *Cost calculator* for large runs. *Run cards*: type, status, the stage progress (discover, sites, Google Maps and socials, photos, writing, checks, ready), plain counts (found, ready, needs a look, missing contact, duplicates, published, average readiness and the template classes), spend against the ceiling, the reason a run stopped with one matching action (continue after topping up, fix the key, raise the ceiling), the review link, pause and cancel; exports, reconciliation, retry and delete are under "more actions".
- **תור הבדיקה** (`/ops/import/review`): the "לבדיקה" tab also has a bulk publish (the selected records, or the whole page): the records are published as they are, their review reasons stay recorded, and only blocking reasons (no contact, no category) still refuse. Per record the source, the website and what kind it is (or the directory link that was dropped), email status, website outcome, notices, services with category and price, a logo and photo picker, the profile checklist with the same readiness score the listing will have, and an evidence table (value, source link, date, confidence, quote). Select records and "בדיקה חוזרת של האתר" to re-read their sites. Approve, merge, edit, reject, mark duplicate, restore. Publish the ready records on the page, or every ready record in a run: a bulk publish creates the listings without copying images (a request on Vercel ends at 60 seconds), works in rounds of about 20 seconds until nothing is left, and then copies the logos and photos of the new listings in small batches, with the progress logged on the screen. "Needs review" records are never bulk-published.
- **השלמות** (`/ops/import/enrich`): every published, unclaimed listing from the import with its readiness, missing sections and the sources that can fill them (filters by region, city, category, status, missing section, source and text). Choose listings and press "complete all gaps": each source runs only for the listings it can help (the step list and manual mode are under "customise"). Batches are listed at the top with their steps, progress, Apify runs, spend, error hints and the continue, pause, cancel and delete controls; finished or stopped batches can be deleted one by one or together. Deleting a batch removes the run, its tasks and its statistics; listing data and spend entries stay. Discovery runs that still own staged records cannot be deleted.
- **דוח פרופילים** (`/ops/import/report`, `src/lib/server/importReport.ts`): the ongoing report of every business the import scraped or completed. Filters by region, city, category, state (published, ready, in review, incomplete, pending, duplicate, rejected, closed), missing section, run and text; summary tiles (published, waiting, complete profiles, average readiness, how many ChatGPT filled, how many have a written description, accumulated cost); a table by city and category with a one-click "complete gaps" batch for the published, unclaimed listings of that group (`enhanceGroupAction`, automatic plan, ceiling from the estimate); then one card per business with the link (the public profile when published, otherwise its review record), a chip per template section (has, honest fallback, missing), what is missing, which sources answered (DataForSEO, the website outcome, Maps, Facebook, Instagram, browser, ChatGPT with the fields it filled), the description's words and model, photo and service counts, cost, last activity and links to the review record and the run. Refreshes on its own while a run is live. `/ops/import/report/export` downloads the same rows as CSV under the same filters.
- **Reset** (bottom of the runs screen, `resetImport` in `src/lib/server/importOps.ts`): wipes every listing the import created (approved records; their business, branch, services, reviews and stored images), then every import record, run, batch, task, observation, spend entry and per-run budget, the website cache and the Google display cache, so all four screens start empty. Kept: claimed listings, listings whose business has an owner, listings with bookings, requests, waitlist entries, gift cards, staff or a second branch, listings that existed before the import (merged records), settings, monthly caps and the audit log. Refused while a worker holds a run. The screen shows the counts first and needs the word מחיקה typed; the deletion is written to `audit_logs` as `import_reset`.
- **Exports** (`/ops/import/export?run=<id>&kind=canonical|audit`): the canonical CSV has only publishable fields (no Google content, no Maps links, provider ratings only when enabled); the audit CSV has counts, reasons, website outcomes, spend per provider and open reconciliation items.

## Costs

Prices are versioned in `src/lib/import/pricing.ts` (override with `IMPORT_PRICING_JSON`). Reference rates for DataForSEO Business Listings Search: **$0.012 per request + $0.00036 per record**, supplied on 2026-09-25 and not fetched (the pricing page was not reachable from the build environment). Google Place Details prices in the file are unverified; confirm them before turning Google on.

- Every paid call reserves its gross maximum before it is sent, with single conditional SQL updates in one transaction against the run budget and each provider cap. Concurrent workers cannot overspend.
- Settling is idempotent: a request key is never billed twice by us.
- Pilot default: 100 records, $1 ceiling. At most one request: $0.012 + 100 x $0.00036 = **$0.048** gross, before tax and any minimum top-up DataForSEO requires.
- `npm run import:dryrun` prints the estimate for 100 / 1,000 / 10,000 businesses without credentials or network.

## Commands

```bash
cd web
npm run import:dryrun                         # cost estimate, no credentials
npm run test:import                           # unit tests + DB tests (DB tests need a local DATABASE_URL)
npm run import:simulate                       # SIMULATED pilot on a mock provider and fixture sites (local DB only), editorial in mock mode
npm run import:manifest                       # regenerate docs/coverage-manifest.md from src/lib/import/coverage.ts
npm run import:screenshots -- --url <listing> # 390 / 768 / 1440px screenshots of a running listing page (Playwright)
npm run import:dfs-categories -- --confirm    # check the category ids against DataForSEO (live, may be billed)
npm run import:work -- --max-minutes 30       # the worker (normally runs in GitHub Actions)
```

The worker resumes where it stopped; a lease makes sure only one worker processes a run.

**Running the worker on your own machine or VPS** instead of GitHub Actions (same code, same environment names):

```bash
cd web
cp .env.worker.example .env.worker            # fill in; the file is ignored by git
docker compose -f docker-compose.worker.yml up -d --build
docker compose -f docker-compose.worker.yml logs -f
```

`Dockerfile.worker` installs Chromium with its system libraries, so the browser fallback and the render step work out of the box; the container loops over queued runs (`IMPORT_MAX_MINUTES` per run, `IMPORT_IDLE_SECONDS` between looks). Without Docker: `npx playwright-core install --with-deps chromium` once, then `npm run import:work` in a loop. The admin's "start worker" button still dispatches the GitHub job; a self-hosted worker simply picks up queued runs on its own, and the two never work the same run thanks to the lease. Keep to one worker per database.

## Source-use constraints

- `src/lib/import/sourcePolicy.ts` says what is kept and published per source. DataForSEO ratings and photos (which come from Google) stay unpublished until the terms are confirmed; record any change in `docs/decisions.md`.
- Logos and photos come only from the business's own website, are chosen by staff, and are copied to our storage. The listing says it is not managed by the business, and the owner can replace or remove them after claiming. Turn `useWebsiteImages` off if that is not acceptable.
- Google content only through the attributed provider view, with the retention above.
- Business contact details of sole traders are personal data under the Israeli Privacy Protection Law (Amendment 13). Confirm the database registration and notice duties with counsel before launch.
- Outreach by email or SMS is subject to section 30A of the Communications Law.
- No scraping of social networks, Google Maps or search results by our own code, and no proxies. The self-hosted crawler and browser read only the business's own website (robots.txt respected, blocks stop the site); social profiles and Google Maps are read only through Apify actors and only when the profile confirms the business; ChatGPT's web search reads public pages and only facts that carry the page URL are kept.
